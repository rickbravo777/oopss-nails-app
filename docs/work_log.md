### 2026-08-09 — Post-delivery iteration #22: `get_service_info` couldn't find a real service if the client's own wording didn't match it as one exact literal substring

- **Work Done**: While doing a pre-meeting smoke test with the client, she typed "como es eso de extension en polygel" (asking about the real catalog service "Extensión Polygel") and the assistant replied it couldn't find any matching service — a real, reproducible search failure, not a hallucination-guardrail false negative.
  - **Root cause**: `getServiceInfoTool`'s handler (`backend/src/lib/ai/tools/getServiceInfo.ts`) matched via a single Postgres `contains` check on the *entire* query string against the service/category name. This breaks two ways a real client's phrasing very commonly diverges from the catalog's exact name: (1) **extra/inserted words** — "extension **en** polygel" is not a contiguous substring of "Extensión Polygel" at all, since there's no "en" in the real name; (2) **missing accents** — Postgres string matching is accent-sensitive by default (`mode: "insensitive"` only handles case), so "extension" (no accent) never matches "Extensión" (with one) as a substring either, independent of issue (1).
  - **The fix**: rewrote the matching strategy — split the query into "significant words" (normalized to strip diacritics and lowercase, with a small Spanish stopword list — "en", "de", "el", "como", "eso", etc. — filtered out so filler words in a natural question don't count as search terms), then fetch all active services and require *every* significant word to appear somewhere in that service's name+category (in any order, not as one contiguous phrase). A query that's only stopwords short-circuits to "not found" without even hitting the DB. Verified this doesn't over-match: added a specific test where two services share a category word ("Manos") but only one also matches a second query word — correctly narrows to the one real match, not both.
  - **Files Created/Modified**: `backend/src/lib/ai/tools/getServiceInfo.ts`, `backend/src/lib/ai/tools/getServiceInfo.test.ts`.
  - **Decisions**: No new DEC entry — a search-quality bug fix within an already-existing tool, not a new pattern. Worth remembering for any *other* free-text-to-catalog matching added later (e.g. term synonyms): exact-substring-of-the-whole-phrase matching is fragile against real client phrasing in ways that only show up in live use, not in code review.
  - **Security Check**: N/A — same read-only catalog lookup, no new surface. Fetching all active services instead of a targeted `WHERE` is a non-issue at this catalog's size (~68 services).
  - **Tests**: Backend suite grew from 193 to 197 (rewrote all of `getServiceInfo.test.ts`'s cases plus 4 new ones: the exact reproducing "extension en polygel" input, accent-symmetric matching, AND-not-OR word matching, and the all-stopwords short-circuit), all passing; `npm run build`/`npm run lint` clean. Verified live with a real OpenAI key: the exact reproducing question now correctly answers with real Extensión Polygel data ($49, 90 min, Tania/Mariangely/Yez); a second accent-dropped test ("cuanto cuesta la depilacion de axila," missing the accent on "depilación") also answered correctly ($8, Sonia, 15 min).

## Residual Risks

Accepted-but-not-fixed risks across the project's history, for reference at delivery. Each pointer leads to the full reasoning; this list only summarizes.

- **`AssistantPolicy` (admin-authored knowledge-base text) has no prompt-injection content sanitization beyond a 2000-char length cap.** Accepted because only an already-fully-trusted authenticated admin can write it, and that admin already has unchecked control over pricing, credentials, and every other sensitive surface in this single-admin-role app. Reconsider if a lower-privilege admin role is ever introduced. See `docs/decision_log.md` DEC-11.

- **`EscalationFlag.resolutionNotes` is a single field reused for both the AI's original escalation-context note and the admin's eventual resolution note** — resolving an escalation overwrites the original note in that column. Low impact: the original note is visible in the admin UI before resolving, and now also recoverable via the full conversation transcript (UJ-19's "Ver conversación" link, added in the `{M3+M4}` review).
